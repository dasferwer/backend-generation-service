# Сервис генерации

FastAPI, PostgreSQL 17, SQLAlchemy 2 с asyncpg, Alembic и httpx. Два фейковых
провайдера, журнал целочисленных токенов и очередь отправки в самой таблице попыток.
Python 3.11+, в контейнере — Python 3.12. Зависимости, включая транзитивные,
зафиксированы в `requirements.txt`; исходные ограничения — в `requirements.in`.

## Запуск

Нужны Docker Engine/Desktop и Docker Compose с поддержкой `service_completed_successfully`
и `up --wait`. Команды выполняются из корня репозитория.

```sh
cp .env.example .env
docker compose up --build -d --wait
curl -fsS http://localhost:8000/health
docker compose exec -T api python scripts/check_workers.py
```

`docker compose up` также работает в обычном режиме с выводом логов. Сначала
поднимается PostgreSQL с проверкой готовности, один контейнер `migrate` применяет
миграции, затем запускаются четыре процесса API и по одному процессу alpha и beta.
Провайдеры и БД доступны внутри сети Compose; наружу опубликован API на `127.0.0.1:8000`.
OpenAPI: <http://localhost:8000/docs>.

В `.env` можно изменить `API_PORT`, секрет и параметры провайдеров. После изменения:

```sh
docker compose up -d --force-recreate api alpha beta
```

Сеть по умолчанию — `10.246.81.0/24`. При пересечении с вашей сетью задайте другую
свободную подсеть через `COMPOSE_SUBNET` в `.env`. Тесты используют отдельную подсеть.

```sh
docker compose logs --tail 50 api alpha beta
docker compose down
```

`down` сохраняет том с данными. Повторный запуск не начисляет стартовый баланс заново.
Демонстрационный пользователь: `user_id=1`, начальное пополнение — 100 токенов,
отдельная строка `initial` в журнале. Каталог и пользователь создаются миграцией.

## Примеры API

```sh
curl -fsS http://localhost:8000/users/1/balance
curl -fsS -X POST http://localhost:8000/generate \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1,"model_slug":"image-fast","prompt":"Море на рассвете","ref_images":[]}'
```

Ответ `202 {"task_id":"..."}` означает, что списание, задача и намерение отправки
зафиксированы. Отправка выполняется фоновыми обработчиками, результат не ожидается.
Подставьте полученный UUID:

```sh
curl -fsS "http://localhost:8000/tasks/$TASK_ID"
curl -fsS 'http://localhost:8000/users/1/balance?limit=20'
```

Баланс и журнал читаются в одной транзакции `REPEATABLE READ`. Журнал отсортирован
по `id DESC`; `limit` от 1 до 100, по умолчанию 20. `current_leg` — последняя
созданная попытка, в том числе у терминальной задачи. `attempts` упорядочены по
приоритету, содержат время, состояние, провайдера и причину ошибки. Пропущенные ноги
в историю не добавляются; `queued` явно обозначает ещё не отправленную попытку.

Подписанный платёж можно отправить из API-контейнера: секрет берётся из его окружения.

```sh
docker compose exec -T api python scripts/request.py \
  http://api:8000/webhooks/payments \
  '{"payment_id":"demo-payment-1","user_id":1,"tokens":10,"status":"succeeded"}'
```

Повтор этой команды не добавит второго начисления. Поддерживаются `pending`, `failed`
и `succeeded`; начисление делает только `succeeded`. После `pending` или `failed`
разрешён `succeeded`. Успешный платёж не откатывается последующим неуспешным событием.
Любой повтор `payment_id` с другим пользователем или количеством токенов — `409`.
Возврат платежей этой моделью не предусмотрен.

Вебхук провайдера: `POST /webhooks/providers/alpha` либо `/beta`:

```json
{"attempt_id":"UUID попытки","external_id":"необязательный ID","status":"completed","result":"https://example.org/result"}
```

```json
{"attempt_id":"UUID попытки","status":"failed","error_type":"technical"}
```

`attempt_id` существует до HTTP-запроса провайдеру и является ключом корреляции.
`external_id` необязателен: ранний вебхук обрабатывается до сохранения ответа POST.
Провайдер в маршруте должен совпадать с владельцем попытки.

Ограничения: `user_id` и платёжные `tokens` — строгие целые числа от 1 до 1 000 000 000
(строки, boolean и дроби не принимаются); `payment_id` 1–128 символов, slug 1–64,
prompt 1–10 000 и не только пробелы; максимум 100 строк референсов по 1–2048 символов.
Каждая нога дополнительно ограничивает количество референсов. Референсы не обрезаются.
Результат провайдера — HTTP(S)-ссылка. Лишние поля запросов запрещены.

Ошибки возвращаются через `detail`: `400` — нет подходящей ноги, `402` — недостаточно
токенов, `429` — уже три активные задачи, `401` — неверная подпись, `409` — конфликт
платежа/провайдера, `404` — неизвестный пользователь, модель, задача, попытка или
провайдер, `422` — нарушение схемы. Некорректный формат UUID также даёт `422`.
`/generate` не имеет клиентского ключа идемпотентности: повтор запроса создаёт новый
заказ и новое списание, если позволяют баланс и лимит.

## Подпись

`X-Signature` — 64 строчных шестнадцатеричных символа HMAC-SHA256 без префикса.
Ключ — UTF-8-байты `WEBHOOK_SECRET`, сообщение — исходные байты HTTP-тела.
Получатель использует `Request.body()` и `hmac.compare_digest`; повторной сериализации
перед проверкой нет. Отправитель подписывает именно те байты, которые отправляет.
Изменение пробелов или кодировки после вычисления подписи делает её неверной.

Секрет в `.env.example` — только демонстрационный. `.env` исключён из Git и образа.
Валидные дубли и поздние события получают `200` без повторных последствий.
Ответ отправляется после коммита; сбой БД даёт ошибку, а не успешное подтверждение.

## Каталог и переходы

| Модель | Цена | Порядок ног: провайдер / max_ref_images / skip_on_moderation |
|---|---:|---|
| image-fast | 2 | alpha / 4 / false → beta / 10 / false |
| video-long | 25 | beta / 2 / false → alpha / 1 / true |

Задача: `active → completed | failed`; терминальные состояния не переоткрываются.
Попытка: `queued → sending → waiting → completed | failed`. Из любого открытого
состояния (`queued`, `sending`, `waiting`) возможны завершение вебхуком или технический
отказ сторожем. Повторный захват после падения оставляет `sending` и обновляет аренду.

- `technical` — следующая нога, подходящая по числу референсов.
- `moderation` — то же, с пропуском ног `skip_on_moderation=true` при этом переходе.
- `payload` — сразу окончательный отказ.
- Синхронные 5xx, 429, ошибка соединения, некорректный ответ или таймаут POST — `technical`.
  Остальные ответы, кроме ожидаемого 202, считаются `payload`.
- Если следующей ноги нет — `failed`, стоимость заказа возвращается в той же транзакции.
  При успехе возврата нет.

Цена и план ног сохраняются в задаче: изменение каталога не меняет существующий заказ.
`PROVIDER_TIMEOUT` по умолчанию 60 секунд отсчитывается с создания каждой попытки,
включая время в очереди. Срок хранится в БД и не продлевается повторными отправками.
Сторож в каждом процессе закрывает просроченные открытые попытки как `technical`.

Поздний `completed` закрытой попытки игнорируется даже при активной следующей ноге.
Он не заменяет её результат, не отменяет возврат и не переоткрывает терминальную задачу.
Если вебхук и сторож конкурируют, побеждает первый зафиксированный переход под
блокировками; второй перечитывает состояние. Само истечение времени без закрытия
попытки ещё не запрещает вебхуку победить в этой гонке.

## Транзакции и восстановление

Во всех бизнес-переходах порядок блокировок один: пользователь → задача → попытка.
При создании заказа блокировка пользователя сериализует проверку баланса и активных
задач. Частичный уникальный индекс `(user_id, slot)` для `active`, со слотами 1–3,
дополнительно запрещает четвёртую активную задачу на уровне БД.

Журнал допускает только добавление. Уникальны `payment_id`, `(task_id, kind)` и
начальное пополнение пользователя. Баланс изменяет только `AFTER INSERT`-триггер
журнала; пропущенная вставка `ON CONFLICT DO NOTHING` его не вызывает. Ограничение
запрещает отрицательный баланс, отложенный триггер проверяет равенство сумме журнала.
Начисление, списание и возврат фиксируются вместе со связанными бизнес-данными.
Вебхуки, сторож и ответы отправителя используют один переход с блокировками;
завершённая задача не получает возврат.

Попытка и намерение отправки создаются одной транзакцией со списанием либо отказом
предыдущей ноги. Обработчики конкурентно захватывают строки через
`FOR UPDATE SKIP LOCKED`, сохраняют новый `lease_token` и **коммитят до HTTP**.
Захват блокирует только попытку и не берёт последующие блокировки пользователя/задачи.

При падении:

- До коммита создания — нет ни заказа, ни списания; после коммита до отправки остаётся `queued`.
- Во время отправки — другой процесс повторно забирает `sending` после истечения аренды.
- Провайдер принял запрос, ответ не сохранён — повторяется тот же `attempt_id`;
  провайдер возвращает прежний `external_id`, вторую генерацию не создаёт.
- Старый владелец аренды вернулся — токен и срок аренды проверяются при сохранении
  ответа и технического отказа. Устаревший ответ ничего не меняет.
- Вебхук пришёл раньше ответа POST — он завершает существующую попытку;
  последующий ответ POST не может вернуть её в `waiting`.
- Процесс упал посреди вебхука — PostgreSQL откатывает транзакцию; повтор вебхука
  выполняет переход заново. Если коммит уже состоялся, повтор не имеет последствий.

Обычный синхронный таймаут POST ведёт на следующую ногу, а не к повтору старой.
Всего не более трёх отправок одной попытки; после исчерпания этого лимита она всё равно
закроется по сохранённому общему сроку. Корректность не зависит от памяти процесса.
В каждом процессе две отправки параллельно; соединения и циклы закрываются через
lifespan. HTTP: connect/write/pool по 1 секунде, read и полный бюджет POST — 3 секунды.
Аренда — 10 секунд. Логи связывают task_id, attempt_id и provider без prompt и секрета;
параметры SQL скрыты при ошибках.

«Ровно один раз» относится к **зафиксированным движениям токенов и переходам состояния**.
HTTP доставляется повторно; единственная сетевая доставка не гарантируется.
Идемпотентность приёма по `attempt_id` — явный контракт обоих фейковых провайдеров;
для реального провайдера такой контракт пришлось бы проверить отдельно.

## Управляемые провайдеры

По умолчанию `POST /tasks` возвращает `202 {"external_id":"..."}`, а через 2–20 секунд
провайдер отправляет успешный подписанный вебхук. Настройки окружения имеют префикс
`ALPHA_` или `BETA_` в Compose:

| Суффикс | Значение по умолчанию | Назначение |
|---|---|---|
| FAILURE_RATE | 0 | Доля failed от 0 до 1; выбор стабилен по attempt_id и провайдеру |
| ERROR_TYPE | technical | technical / moderation / payload |
| POST_MODE | normal | normal / 503 / timeout |
| DELAY_MIN, DELAY_MAX | 2, 20 | Задержка вебхука, секунды |
| DUPLICATES | 1 | 2 отправляет два одинаковых вебхука одновременно |
| NO_WEBHOOK | false | Полностью отключает вебхук для новых задач |

Настройки фейка можно заменить без перезапуска подписанным `/settings` внутри сети
Compose. Неуказанные поля возвращаются к значениям по умолчанию. Уже принятый запрос
хранит свой сценарий в PostgreSQL; новые настройки и перезапуск его не меняют.

```sh
docker compose exec -T api python scripts/request.py http://alpha:8000/settings \
  '{"failure_rate":1,"error_type":"technical","delay_min":0.1,"delay_max":0.1}'
docker compose exec -T api python scripts/request.py http://beta:8000/settings \
  '{"delay_min":0.1,"delay_max":0.1,"duplicates":2}'
```

После этих команд `image-fast` проходит alpha → beta. Другие сценарии:

| Сценарий | Настройка `/settings` | Заказ |
|---|---|---|
| Последняя нога отказывает | beta: `{"failure_rate":1}` | image-fast с 5 референсами |
| Moderation пропускает alpha | beta: `{"failure_rate":1,"error_type":"moderation"}` | video-long |
| Payload без fallback | alpha: `{"failure_rate":1,"error_type":"payload"}` | image-fast |
| Синхронный 503 | alpha: `{"post_mode":"503"}` | image-fast |
| Синхронный таймаут | alpha: `{"post_mode":"timeout","no_webhook":true}` | image-fast |
| Нет вебхука, возврат | beta: `{"no_webhook":true}` | image-fast с 5 референсами |
| Поздний completed | beta: `{"delay_min":62,"delay_max":62}` | image-fast с 5 референсами |
| Ранний completed | alpha: `{"post_mode":"timeout","post_delay":2,"delay_min":0,"delay_max":0}` | image-fast |
| Обычный режим | alpha и beta: `{}` | любой допустимый заказ |

В режиме timeout запрос принимается и задерживает ответ на `post_delay` (по умолчанию
5 секунд). В режиме 503 вебхука нет. Принятые задания и доставка вебхуков хранятся
в БД; после падения доставка восстанавливается с арендой. Неуспешная доставка
повторяется максимум восемь раз с задержкой 2, 4, 8, 16, затем до 30 секунд.
Дубли имеют одинаковые байты и подпись. Длительная недоступность API после этих
попыток требует ручного повтора; задача при отсутствии результата закрывается сторожем.
Для разных сценариев используйте свежие заказы и сбрасывайте настройки обоих провайдеров.

## Проверки

Полный цикл в отдельном Compose-проекте:

```sh
./scripts/check.sh
```

Скрипт собирает образы, создаёт отдельный том PostgreSQL и сеть, проверяет реальные
четыре дочерних процесса API, запускает Ruff и pytest. По завершении удаляет только
собственные тестовые контейнеры, сеть и том. Основной демонстрационный сервис и его
данные не затрагиваются. Секрет тестового проекта всегда демонстрационный и не
зависит от секрета основного `.env`. Порт тестового API — 18081, подсеть — `10.246.82.0/24`;
при необходимости задайте `CHECK_API_PORT` и `CHECK_SUBNET`.

```sh
./scripts/check.sh -m 'not slow'
./scripts/check.sh -m slow
```

`slow` — отдельный сценарий с настоящим ожиданием 60 секунд и вебхуком через 62 секунды;
в нём сроки в БД не переписываются. В быстрых гонках время переводится сохранённым
сроком в БД. Интеграционные тесты создают уникальную схему на каждый тест; HTTP-тесты —
своих пользователей внутри отдельной тестовой БД. SQLite не используется.

Проверяются 20 конкурентных дублей оплаты, 10 отказов с единственным возвратом,
fallback с двумя попытками и без возврата, поздний completed после возврата и при
активной следующей ноге; также баланс и сумма журнала, конкурентные заказы, конфликты
оплаты, подпись, moderation/payload, 503/таймаут, отсутствие вебхука, гонки сторожей,
ранний вебхук, потеря ответа и смена владельца аренды. Ошибка БД посреди вебхука
проверяется с откатом и повторной доставкой. Конкурентные запросы стартуют через
барьер и используют отдельные транзакции/соединения. Ожидания состояния ограничены.

## Миграции и структура

Миграции не запускаются каждым API-процессом. Для остановленного сервиса:

```sh
docker compose run --rm migrate alembic current
docker compose run --rm migrate alembic upgrade head
```

Для следующей миграции, в локальном Python-окружении с установленными зависимостями:

```sh
python3.11 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
alembic revision -m 'Описание изменения схемы'
```

Заполните `upgrade`/`downgrade` в новом файле `migrations/versions`, обновите определения
таблиц в `app/db.py`, проверьте миграцию на отдельной БД и пересоберите контейнеры.
Миграции пишутся явно: определения Core не содержат всех триггеров и индексов для
безопасного автоматического вывода изменений. Откат начальной миграции уничтожает
таблицы и допустим только на одноразовой тестовой БД.

`app/api.py` — HTTP и жизненный цикл; `service.py` — транзакционные бизнес-переходы;
`worker.py` — отправка и сторож; `fake_provider.py` — оба провайдера;
`db.py`, `schemas.py`, `security.py`, `config.py` — таблицы, контракты, подпись и настройки.

Решение демонстрационное: нет пользовательской авторизации, реальных денег,
хранилища файлов и реальных внешних провайдеров. Референсы — строки, результат — ссылка.
API и управляющие ручки фейков нельзя публиковать наружу без отдельной защиты.
